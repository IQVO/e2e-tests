Golden-path bootstrap (bootstrap.feature): one work unit flowing through every bounded context — facility-layout's map, inventory stock, workforce shift plan (Kafka→wes labor-plan-view), wes release (Kafka→fulfillment task creation), task completion (Kafka→wes read model) — exercising both sync HTTP and async Kafka integration Cross-context integration proofs: facility-layout map propagation to inventory-storage (Open Host Service/Published Language, conformist consumer), order-management choreographed release (POST /orders allocates synchronously and publishes OrderAllocated that wes turns into a real work unit), promise/re-promise feedback loop across three contexts and three topics (ADR 0014) Agentic decision-support proof (flow_balance_exception.feature): seeds three independent signals (saturated wes pool, workforce staffing gap, stuck fulfillment task) and warehouse-ops-agent must correlate them over real MCP servers of all five contexts into a ranked FlowBalanceException with a full evidence trail, plus surfacing it in its daily brief Lifecycle harness: scripts 01-06 build all 12 binaries (6+ HTTP services, 5 MCP servers, ops-agent), start them with PID-file tracking (kills only what it started), and tear down cleanly; env.sh is the single source of truth for ports, DB URLs and MCP keys Sustained-load soak (soak_backlog_ramp.feature, @soak): ramps backlog into pick-soak/pack-soak paths over a default 1h while configurable picker/packer pools claim and complete tasks; observational (409s counted, not failed), tunable via SOAK_* env vars, excluded from default runs Pure-consumer and catalogue coverage: labor-performance scoring a completed task against its engineered standard (only proof the TaskCompleted consumer delivers) and process-path-management's full REST lifecycle + Kafka publication as the fleet's declared process-path catalogue

Risks & Watchouts

Not in CI: the full godog suite runs only locally, so a green CI badge says nothing about end-to-end behaviour — regressions surface at the weekly cross-repo run or on a developer's machine

Multi-repo coupling: requires all sibling repos checked out under one root with matching branches; a sibling's compile break or contract change breaks this harness's run

Shared-broker risk: the harness joins the same shared Kafka broker the kind cluster uses — the historical hardcoded-consumer-group incident (wes#67…
